# Финмодель «Спартак»

Правила модели, её устройство и контракт правки — в `CLAUDE.md`. Прочитайте
его прежде, чем что-либо делать.

## Режимы

Пользователь пишет `/finmodel` с уточнением. Разберитесь, чего он хочет, и
идите по нужной ветке.

| Запрос | Что делать |
|---|---|
| `/finmodel` без уточнения, «проверь модель» | полный цикл, ниже |
| «что не так», «найди ошибки» | аудит — агент `finmodel-auditor` |
| «что будет, если …» | прогон с подстановкой — агент `finmodel-tester` |
| «реалистично ли …», «сходится ли с фактом» | агент `finmodel-economist` |
| «поправь …» | агент `finmodel-builder`, но только после подтверждения |
| «отчёт», «покажи цифры» | прогон + сводка, без правок |

## Полный цикл

```bash
python3 tools/run_model.py --tag база --keep          # ~12 с, даёт книгу со значениями
python3 tools/extract_model.py --model build/recalc/база.xlsx   # карта -> build/
python3 tools/audit_model.py                          # статические проверки
python3 -m pytest tests -q                            # 38 тестов экономики
python3 tools/baseline.py                             # сверка ключевых цифр
```

Порядок именно такой: карта строится по **пересчитанной** книге, потому
что в исходнике нет значений формул — openpyxl их не пишет, и аудит без
них слеп.

Дальше разберите то, что нашлось, и доложите пользователю: что проверено,
что важного найдено, что требует его решения. Пустой результат — тоже
результат, скажите об этом прямо.

## Ответ на «что будет, если»

```bash
python3 tools/extract_model.py --grep "роялти"        # найти вводную
python3 tools/run_model.py --set '01_Вводные!B58=0.07' --tag проба
python3 tools/run_model.py --compare база проба
```

Всегда показывайте «было → стало → дельта» по EBITDA, деньгам, детям и
школам. И называйте границу: при каком значении вводной модель уходит в
убыток или в кассовый разрыв.

Подставлять можно только вводные с листа `01_Вводные`. Подстановка в
формулу отклоняется — иначе «прогон» молча ломает расчёт.

## Правка

Порядок: сформулировать → согласовать → внести → замерить → записать.

1. Опишите правку пятью пунктами (проблема, причина, решение, финансовый
   эффект, проверки) и покажите пользователю.
2. Экономику меняйте только после прямого «да». Представление, формат,
   подписи — можно сразу.
3. Вносите через `finmodel-builder`: правка живёт в `tools/`, не в
   ручном редактировании книги.
4. После правки — весь цикл заново. Тесты, аудит и эталон должны быть
   зелёными или объяснёнными.
5. Запишите в `docs/Журнал_правок.md`.

## Чего не делать

- Не менять экономическую логику без подтверждения владельца.
- Не приравнивать партнёров к школам и не заменять постепенный набор
  детей полной загрузкой — это два правила, которые ломают модель тише
  всего.
- Не смешивать БДР и БДДС.
- Не решать за владельца семь открытых вопросов из `CLAUDE.md`.
- Не править тест ради зелёного прогона: сначала докажите, что тест устарел.
- Не обновлять `tests/baseline.json` без объяснения, что сдвинуло цифры.

## Если что-то не работает

- `LibreOffice не пересчитала книгу` — проверьте, что стоит Calc:
  `ls /usr/lib/libreoffice/program/ | grep calc`. Без пакета
  `libreoffice-calc` файл просто не открывается.
- `нет build/model_map.json` — сначала `python3 tools/extract_model.py`.
- Тесты падают все разом — скорее всего, сбился срез: удалите
  `build/runs/` и прогоните заново.
- Сомневаетесь, ловят ли тесты ошибки — `python3 tools/selfcheck.py`.
